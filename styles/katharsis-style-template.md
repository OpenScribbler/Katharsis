# {Exchange type}

{Two or three sentences. What the user is doing when they send this kind of message, and
what they intend to do with your reply. Write it in terms of their next action, not in terms
of the message's grammar: the point of the file is to predict what they need next.}

## Cues

{The phrasings that mark this type, drawn from their real messages. Group by the shape of
the cue, and give a real example for each. Include the near-misses that look like this
type but are not, and name the type they actually are.}

## Ceiling

{One number, in words, and the sentence that makes it obvious why. Also the floor when
this type has one, such as "never end the turn without prose". Ceilings are the shape of
the reply, not a budget to spend: come in under it whenever the answer is done sooner.}

## Shape

{The ordered slots of the reply. First line, then body, then close. Say what goes in each
slot and what never does. Where an element is conditional, give the condition
("codes only when the report carries two or more live decisions"). This is the section
you will actually follow while writing, so write it as instructions, not as description.}

When the message also carries an idea the user is weighing — a proposal, a framing, an
"am I right that…?" — take a position on it in one sentence with the reason attached, at
the point where that part falls in their message. That sentence is the whole of what the
idea gets here; the plan and the second question stay out.

## Reference codes

{Two or three sentences: the codes this type usually carries, the ones it sometimes carries, and the sentence every file repeats: that the list is what is common here rather than a requirement or a limit, and that the full set lives in the "Reference codes" section of the Katharsis output style and of `README.md`.}

## Ambiguities

{The judgment calls this type produces, each as a "When X, do Y" rule with the reason in
the same sentence. These are the cases where the shape above does not decide the answer
on its own: the request that changes type mid-turn, the approval that carries a hidden
new constraint, the question whose answer is "it depends". This section is the reason the
file exists; the rules above are the easy part.}

## Verification

{What must be true before you claim anything in this reply type, and how you check it.
Reading the source before asserting what it says, running the build before "done",
checking the current state before reporting it. Only the checks this type actually needs.}

## Example

{One short exchange. the user's message, then the reply that served, and one sentence on
what made it land. Keep the reply short enough to read at a glance; a long example
teaches the wrong lesson about length.}
